# NoDeskClaw 修复方案 PRD v6.3.2 Hotfix

版本：v6.3.2 hotfix  
范围：`nodeskclaw-backend`（主）、`hermes-agent` / `copilot-desktop`（消费契约对齐）  
主题：执行层统一为 `hermes_api_server` + 双入口权限分轨 + `RuntimeSkillRunService` 收敛任务创建  
前置依赖：v6.3、v6.3.1 已落地（`execution_contract`、Worker 契约保护、`request_snapshot` 等）  
状态：修复型 PRD / Implementation Guide

---

## 1. 背景

### 1.1 v6.3 / v6.3.1 已解决的问题

v6.3 将组织 MCP（`POST /api/v1/hermes/mcp`）上的 Runtime Skill 固定到：

```text
route_snapshot.route_type = hermes_api_server
execution_contract.runtime_invocation = chat_completions
Worker → /v1/chat/completions
SSE → GET /api/v1/hermes/tasks/{task_id}/events
```

v6.3.1 进一步保证：带 `chat_completions` 契约的任务**禁止**误入 `/v1/runs`。

### 1.2 v6.3.2 要解决的问题

当前仍存在**入口与执行分叉**，导致前端（尤其 hermes-agent）混乱：

| 现象 | 根因 |
|------|------|
| Expert `tools/list` 返回 `customer-profiling`，组织 MCP 返回 `hermes_market-profiling__customer-profiling` | 两套网关命名空间不同（设计如此，但执行层未统一时前端需自行映射） |
| Expert `tools/call` 仍走 `expert_agent_event_stream` → `/v1/runs` | `ExpertRunService._build_expert_route_snapshot()` 写死旧路由 |
| `structuredContent` 字段 Expert 用 camelCase，组织 MCP 用 snake_case | 两套任务创建逻辑各自拼装响应 |
| hermes-agent 配 MCP 与 chat 模式难以共用一套 SSE 消费代码 | 返回契约不统一 |

### 1.3 v6.3.2 产品规则（四条）

```text
1. 执行层唯一：所有 Runtime Skill 异步任务最终 route_type=hermes_api_server，共用同一 Task SSE。
2. 入口双轨、权限分轨：
   - Expert 入口：Expert 权限 + 短 skill 名（hermes-agent 用）
   - 组织 MCP 入口：Skill Grant + 长 tool 名（Desktop / 治理用）
3. 共享内部服务：RuntimeSkillRunService.start(...) 统一创建 HermesTask + SSE token + 标准响应。
4. 返回格式统一：structuredContent 只保留 snake_case 一套，前端零适配。
```

### 1.4 与 v6.3 原文的差异说明

v6.3 原文倾向「Desktop 只调组织 MCP」。v6.3.2 **不推翻**组织 MCP 作为 Desktop / 治理主入口，但**明确允许** Expert Gateway 作为 hermes-agent 的目录门面，只要执行层与 SSE 与组织 MCP 完全一致。

```text
v6.3 保留：组织 MCP = Runtime Skill 注册 + 细粒度授权 + 长 tool 名
v6.3.2 新增：Expert Gateway = 专家目录 + Expert 权限 + 短 skill 名，执行复用同一引擎
v6.3.2 不变：gateway_sequential 团队编排、sync_legacy 同步调试仍可走旧路径（非本 PRD 主路径）
```

## 2. 修复目标

### 2.1 必须达成

```text
1. Expert Gateway 默认 tools/call（event_stream 模式）创建的任务 route_type=hermes_api_server。
2. Expert 与组织 MCP 均通过 RuntimeSkillRunService 创建 HermesTask，消除重复逻辑。
3. 两条入口 tools/call 返回同一套 snake_case structuredContent。
4. 两条入口创建的异步任务均订阅同一 SSE：GET /api/v1/hermes/tasks/{task_id}/events。
5. Expert 入口不依赖 register-to-org-mcp，不经过 HermesSkillAuthorizationService.can_invoke。
6. 组织 MCP 入口保持现有 Skill Grant 与固定路由逻辑不变。
7. Expert 入口写入 request_trace_id / request_snapshot / route_diagnostics（与 v6.3.1 对齐）。
8. ExpertInvocationLog 继续写入，并与 HermesTask 关联。
```

### 2.2 不做

```text
1. 不改 Expert / 组织 MCP 对外 URL 与 tools/list 的 name 命名规则。
2. 不强制 hermes-agent 从 Expert 入口迁移到组织 MCP。
3. 不删除 gateway_sequential、sync_legacy、真正的 /v1/runs 团队编排兼容路径。
4. 不把 Expert 权限与组织 Skill Grant 合并为一套表。
5. 不要求 Expert 发布时自动 register-to-org-mcp。
6. 不改 Desktop / hermes-agent UI 布局（仅消费契约对齐）。
```

## 4. 前端表现变化

### 4.1 hermes-agent / 专家调用 — tools/call 返回与 SSE

**总结**：专家入口 `tools/call` 返回字段从 camelCase 改为与组织 MCP 一致的 snake_case；SSE 订阅逻辑可与组织 MCP 共用一套代码，不再维护两套字段映射。

**元素级变化**：

- `structuredContent.taskId` → **删除**，统一为 `task_id`
- `structuredContent.taskNo` → **删除**，统一为 `task_no`
- `structuredContent.eventSseUrl` → **删除**，统一为 `event_stream`（带 token 的完整 URL）
- `structuredContent.eventUrl` → **删除**，统一为 `event_url`
- `structuredContent.artifactUrl` → **删除**，统一为 `artifact_url`
- **新增** `result_url`、`execution_mode`、`wait_strategy`、`committed`（与组织 MCP 一致）
- **保留** Expert 语义字段：`invocation_id`（原 invocationId）、`catalog_kind`、`catalog_slug`、`skill_name`（短名，便于目录 UI 展示）
- SSE 事件监听：仍订阅 `task.started` / `task.progress` / `task.completed` / `task.failed` / `task.artifact.ready`，**事件名不变**
- 任务进度 Timeline：**不再依赖** Hermes `/v1/runs` 的 delta，与组织 MCP 路径 Timeline 粒度一致（阶段级，非 token 级）

**改动前**（Expert tools/call 返回）：

```text
structuredContent:
  taskId, taskNo, eventSseUrl, artifactUrl, orchestrationMode=agent_event_stream
  → 前端需 normalize 后才能接 SSE
```

**改动后**（与组织 MCP 一致）：

```text
structuredContent:
  task_id, task_no, event_stream, artifact_url, result_url, execution_mode=async_event
  catalog_kind, catalog_slug, skill_name, invocation_id
  → 前端一套 TaskRuntime 模型即可
```

### 4.2 hermes-agent MCP 模式 vs chat 模式

**总结**：两种模式在「触发专家 skill 异步任务」后，共用同一套 `structuredContent` + SSE 消费逻辑；差异仅在发现技能时走哪条 `tools/list`。

**元素级变化**：

- **MCP 连 nodeskclaw**：可继续连 `POST /api/v1/hermes/mcp`（长 tool 名）或 `POST /api/v1/expert/mcp/{slug}`（短 skill 名）；`tools/call` 后处理逻辑**合并为同一函数**
- **chat 触发专家任务**：走 Expert 入口时不再在代理层把 `customer-profiling` 映射为 `hermes_*__*`；直接 `tools/call` Expert 入口，由后端统一执行
- 错误提示：不再出现 `Runtime Skill tool not found for expert ...` 类客户端映射错误（执行由后端 Expert 入口直接创建 `hermes_api_server` 任务）

### 4.3 copilot-desktop / Portal

**总结**：组织 MCP 入口行为不变；Expert 入口若仍被 Desktop 使用，其 `tools/call` 返回格式与组织 MCP 对齐，Desktop 可删除 camelCase 适配层。

**元素级变化**：

- Desktop 任务窗口：Expert 来源任务与组织 MCP 来源任务 Timeline **展示一致**（同一 SSE 端点、同一事件名）
- 专家调用日志页：Expert 来源任务 `route_type` 显示为 `hermes_api_server`（不再显示 `agent_event_stream`）
- Portal 管理端：无新增页面；Expert 发布流程不变，**不要求**额外「注册到组织 MCP」步骤（hermes-agent 场景）

## 5. 入口契约（对外不变部分）

### 5.1 Expert Gateway

| 项 | 约定 |
|----|------|
| 发现 | `POST /api/v1/expert/mcp/{slug}`，`method: tools/list` |
| 调用 | `POST /api/v1/expert/mcp/{slug}`，`method: tools/call` |
| `params.name` | 短 skill 名，如 `customer-profiling` |
| `params.arguments` | `{ "prompt": "...", "context": { ... } }`，`prompt` 必填 |
| 禁止字段 | `_routing`、`_execution`、`route_config` |
| 权限 | `expert_skill:invoke` + skill `is_public` + `call_enabled` |
| 默认模式 | `event_stream`（无 Header 或 `X-NoDeskClaw-Expert-Run-Mode: event_stream`） |
| 兼容 | `sync_legacy` Header 仍走同步 `ExpertMcpProxyService`，**不经过** `RuntimeSkillRunService` |

### 5.2 组织 MCP Skill Gateway

| 项 | 约定 |
|----|------|
| 发现 | `POST /api/v1/hermes/mcp`，`method: tools/list` |
| 调用 | `POST /api/v1/hermes/mcp`，`method: tools/call` |
| `params.name` | 长 tool 名，如 `hermes_market-profiling__customer-profiling` |
| `params.arguments` | 同 Expert |
| 权限 | `skill:invoke` + `HermesSkillAuthorizationService.can_invoke` |
| 前置 | Runtime Skill 已 `register-to-org-mcp` |

### 5.3 命名映射（仅文档说明，前端不应自行拼接）

```text
hermes_{agent_profile}__{skill_name}
  = build_tool_name(agent_profile, skill_name)

示例：
  agent_profile = market-profiling
  skill_name    = customer-profiling
  tool_name     = hermes_market-profiling__customer-profiling
```

Expert 入口由 URL `{slug}` 提供专家身份，故 `tools/list` / `tools/call` 只需短 skill 名。

## 6. 统一 structuredContent 契约（snake_case）

两条入口在 `tools/call` 成功且为默认异步模式时，`result.structuredContent` **必须**符合以下结构（组织 MCP 现有字段为基准，Expert 入口追加目录字段）：

```json
{
  "task_id": "uuid",
  "task_no": "TASK-xxxx",
  "status": "running",
  "execution_mode": "async_event",
  "tool_name": "hermes_market-profiling__customer-profiling",
  "event_stream": "/api/v1/hermes/tasks/{task_id}/events?token=sse_...",
  "event_url": "/api/v1/hermes/tasks/{task_id}/events",
  "event_token_url": "/api/v1/hermes/tasks/{task_id}/events-token",
  "artifact_url": "/api/v1/hermes/tasks/{task_id}/artifacts",
  "result_url": "/api/v1/hermes/tasks/{task_id}/result",
  "artifact_mode": "pull_only",
  "server_artifacts": [],
  "wait_strategy": {
    "type": "sse",
    "fallback": "poll",
    "poll_url": "/api/v1/hermes/tasks/{task_id}",
    "poll_tool": "nodeskclaw_task_wait",
    "result_url": "/api/v1/hermes/tasks/{task_id}/result"
  },
  "message": "任务已启动，请等待事件流通知完成",
  "committed": true,

  "entrypoint": "expert_mcp_gateway",
  "task_source": "expert_mcp",
  "catalog_kind": "expert",
  "catalog_slug": "market-profiling",
  "skill_name": "customer-profiling",
  "invocation_id": "expert-invocation-log-id",
  "agent_profile": "market-profiling",
  "runtime_skill_id": "customer-profiling"
}
```

字段说明：

| 字段 | 组织 MCP | Expert 入口 |
|------|----------|-------------|
| `task_id` ~ `wait_strategy` | 必填 | 必填（同结构） |
| `entrypoint` | `mcp_skill_gateway` | `expert_mcp_gateway` |
| `task_source` | `org_mcp` | `expert_mcp` |
| `catalog_kind` / `catalog_slug` | 可省略 | 必填 |
| `skill_name` | 可省略（tool_name 已编码） | 必填（短名） |
| `invocation_id` | 可省略 | 必填（ExpertInvocationLog.id） |
| `tool_name` | 必填 | 必填（`upstream_tool_name`） |

**禁止**再返回 camelCase 字段（`taskId`、`eventSseUrl` 等）。若需过渡期兼容，可在后端打 `deprecated_fields` 日志，但响应体不双写。

## 7. RuntimeSkillRunService 设计

### 7.1 新文件

```text
app/services/hermes_skill/runtime_skill_run_service.py
```

### 7.2 职责

```text
1. 接收统一的 StartRuntimeSkillRunRequest（见 7.3）。
2. 构建 route_snapshot（hermes_api_server + force_instance）。
3. 写入 execution_contract（v6.3.1 契约）。
4. 调用 TaskService.create_task。
5. 写入 request_trace_id / request_snapshot / route_diagnostics（若调用方传入）。
6. 调用 TaskEventTokenService.create_token。
7. 返回 RuntimeSkillRunResult（含 structuredContent dict）。
8. 不处理权限——权限由调用方（Expert / McpToolMapper）在调用前完成。
```

### 7.3 StartRuntimeSkillRunRequest（概念模型）

```python
@dataclass
class StartRuntimeSkillRunRequest:
    org_id: str
    user_id: str
    tool_name: str                    # hermes_{profile}__{skill}
    runtime_skill_id: str             # 短 skill 名
    agent_profile: str
    hermes_agent_instance_id: str     # HermesAgentInstance.id（绑定记录 id）
    agent_id: str | None              # DeskClaw instance_id（Pod 实例）
    arguments: dict[str, Any]
    client_context: dict[str, Any]    # 含 source、entrypoint、catalog_* 等
    output_policy: dict[str, Any]
    timeout_seconds: int | None
    request_trace_id: str | None
    request_snapshot: dict | None
    route_diagnostics: dict | None
    task_source: str                  # org_mcp | expert_mcp
    installation_id: str | None       # 组织 MCP 有；Expert 为 null
```

### 7.4 route_snapshot 标准结构

Expert 与组织 MCP 创建的 Runtime Skill 任务必须使用：

```json
{
  "route_type": "hermes_api_server",
  "force_instance": true,
  "hermes_agent_instance_id": "...",
  "agent_profile": "market-profiling",
  "runtime_skill_id": "customer-profiling",
  "hermes_instance_name": "market-profiling",
  "timeout_seconds": 900
}
```

Expert 入口可附加审计字段（不影响 Worker）：

```json
{
  "catalog_kind": "expert",
  "catalog_slug": "market-profiling",
  "upstream_tool_name": "hermes_market-profiling__customer-profiling"
}
```

### 7.5 execution_contract 标准结构

```json
{
  "mode": "async_event",
  "timeline_provider": "nodeskclaw_task_events",
  "runtime_invocation": "chat_completions",
  "desktop_route_override_allowed": false
}
```


## 11. 验收标准

### A1. Expert 默认异步调用不再进入 `/v1/runs`

```http
POST /api/v1/expert/mcp/market-profiling
{
  "jsonrpc": "2.0",
  "id": "1",
  "method": "tools/call",
  "params": {
    "name": "customer-profiling",
    "arguments": {
      "prompt": "测试客户画像",
      "context": { "source": "hermes-agent" }
    }
  }
}
```

数据库期望：

```sql
select
  task_no,
  hermes_run_id,
  tool_name,
  routing_metadata->'route_snapshot'->>'route_type' as route_type,
  routing_metadata->'execution_contract'->>'runtime_invocation' as runtime_invocation,
  client_context->>'source' as client_source
from hermes_tasks
where task_no = '<TASK_NO>';
```

```text
route_type = hermes_api_server
runtime_invocation = chat_completions
hermes_run_id is null
client_source = expert_mcp_gateway
tool_name = hermes_market-profiling__customer-profiling
```

### A2. structuredContent 统一 snake_case

Expert 与组织 MCP 的 `tools/call` 响应：

```text
必须含：task_id, task_no, event_stream, artifact_url, result_url, execution_mode, committed
不得含：taskId, taskNo, eventSseUrl, artifactUrl（响应体）
```

### A3. SSE 端点一致

两入口创建的任务均可：

```text
GET /api/v1/hermes/tasks/{task_id}/events?token=...
```

收到 `task.started` → `task.progress` → `task.completed`（或 `task.failed`）。

### A4. Expert 无需组织 Skill Grant

未执行 `register-to-org-mcp` 时：

```text
Expert tools/call 成功（具备 expert 权限 + skill 公开可调用）
组织 MCP tools/call 同一 skill 可能 tool_not_found 或 permission_denied（符合预期）
```

### A5. 组织 MCP 回归

已注册 Runtime Skill 通过 `POST /api/v1/hermes/mcp` 调用，行为与 v6.3.1 一致（route、SSE、产物、去重）。

### A6. sync_legacy 不受影响

```http
X-NoDeskClaw-Expert-Run-Mode: sync_legacy
```

仍同步返回 upstream 结果，**不**创建 HermesTask（或走既有 sync 逻辑），不作为本 PRD 验收项。

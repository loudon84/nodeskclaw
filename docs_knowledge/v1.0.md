# nodeskclaw-knowledge 架构设计方案

**版本：v1.0**
**目标版本：RAGFlow v0.24.0**
**定位：企业知识治理、权限、安全检索与 RAGFlow Adapter**

---

# 1. 产品定位

`nodeskclaw-knowledge` 不替代 RAGFlow，也不修改 RAGFlow 数据结构。

整个系统职责划分为：

```text
nodeskclaw-backend
    │
    │ 用户 / Organization / OrgMembership
    │ JWT
    ▼
nodeskclaw-knowledge
    │
    ├── Knowledge Base 管理
    ├── Knowledge Set 管理
    ├── Source File Registry
    ├── ACL / 权限计算
    ├── 文件版本管理
    ├── RAGFlow Adapter
    ├── Retrieval Security Gateway
    └── Audit
            │
            ▼
        RAGFlow v0.24
        ├── Dataset
        ├── Document
        ├── Chunk
        ├── Parser
        ├── Embedding
        └── Retrieval
```

核心原则：

```text
RAGFlow
负责：
“哪些知识和问题语义相关”

nodeskclaw-knowledge
负责：
“这个用户有没有权限看到这些知识”
```

RAGFlow v0.24.0 已提供 Dataset CRUD、Document 上传、Document `meta_fields`、解析、跨 Dataset Retrieval 和 metadata filtering，因此这些能力可以全部通过官方 HTTP API 对接，无需修改 RAGFlow 内部代码。

# 2. 最重要的领域映射

这里必须解决一个名称冲突：

RAGFlow 本身把一个“知识库”称为：

```text
Dataset
```

而我们的桌面端又需要：

```text
多个知识库
    ↓
组成一个数据集
    ↓
给大模型统一检索
```

因此内部不要继续使用 `dataset` 同时表示两个东西。

建议统一：

| nodeskclaw 领域   | RAGFlow 对象          | 含义           |
| --------------- | ------------------- | ------------ |
| `KnowledgeBase` | Dataset             | 一个物理知识库      |
| `SourceFile`    | Document            | 一个逻辑源文件      |
| `FileVersion`   | Document            | 源文件的某一个实际版本  |
| Chunk           | Chunk               | RAGFlow 自动产生 |
| `KnowledgeSet`  | 无直接对象               | 多知识库检索集合     |
| Retrieval       | `/api/v1/retrieval` | 跨知识库检索       |

桌面端中文仍然可以显示：

```text
知识库
数据集
```

但代码内部推荐：

```text
knowledge_base
knowledge_set
```

不要定义：

```text
nodeskclaw dataset
```

避免以后和：

```text
ragflow_dataset_id
```

混淆。

# 3. KnowledgeSet 不需要在 RAGFlow 创建新的 Dataset

这是本方案最重要的架构决定之一。

例如：

```text
销售知识数据集
│
├── 产品知识库
├── 销售制度知识库
└── 客户案例知识库
```

RAGFlow 中仍然只是：

```text
dataset-A
dataset-B
dataset-C
```

nodeskclaw-knowledge 保存：

```text
knowledge_set
    ├── KB-A
    ├── KB-B
    └── KB-C
```

检索时转换成：

```json
{
  "question": "...",
  "dataset_ids": [
    "ragflow_dataset_a",
    "ragflow_dataset_b",
    "ragflow_dataset_c"
  ]
}
```

RAGFlow v0.24.0 的 `/api/v1/retrieval` 原生接受多个 `dataset_ids`，因此没有必要复制文档、迁移 Chunk 或在 RAGFlow 建立一个新的“聚合 Dataset”。

于是：

```text
KnowledgeSet
只是 nodeskclaw 的逻辑对象

而不是
RAGFlow 的物理对象
```

这完全满足：

> 不改变 RAGFlow 产品原结构。

# 4. 用户体系

## 4.1 不建立 Knowledge User 表

`nodeskclaw-knowledge` 不维护：

```text
knowledge_users
```

也不复制员工。

用户唯一来源：

```text
nodeskclaw-backend
```

当前 `nodeskclaw-backend` 中，员工在某个组织中的实际身份由 `OrgMembership` 表达，它已经包含：

```text
user_id
org_id
role
job_title
department
employee_no
supervisor_membership_id
```

因此知识权限的核心 Principal 应定义为：

```text
member_id = OrgMembership.id
```

而不是：

```text
user_id
```

因为同一个 User 将来可能同时属于多个 Organization，而权限实际属于：

```text
User × Organization
```

这个关系正是 `OrgMembership`。

# 5. Member Context

桌面端继续使用：

```text
nodeskclaw JWT
```

请求：

```text
Copilot Knowledge
        ↓
Authorization: Bearer <JWT>
        ↓
nodeskclaw-knowledge
```

但 `nodeskclaw-knowledge` 不应该重新维护用户数据库。

建议在 `nodeskclaw-backend` 增加一个非常小的内部接口：

```http
GET /api/v1/auth/knowledge-context
Authorization: Bearer <JWT>
```

返回：

```json
{
  "user_id": "user_001",
  "member_id": "member_001",
  "org_id": "org_001",

  "name": "张三",
  "employee_no": "E1001",
  "department": "销售中心",

  "member_role": "member",

  "is_active": true,
  "is_super_admin": false
}
```

当前 `/auth/me` 已经能够根据 JWT 获取用户并查询组织成员角色，但没有将 `OrgMembership.id / department / employee_no` 作为完整 Knowledge Principal 返回，因此增加一个专用 Context API 比让 Knowledge Service 直接读取 backend 数据库更合理。

当前 JWT 校验本身也已经会检查：

```text
User 是否存在
User 是否 active
Token 类型
Token 过期时间
```

这些继续由 backend 负责。

不建议把：

```text
department
role
权限列表
```

长期写死在 JWT 中。

因为组织成员权限发生变化以后，旧 Token 会继续持有旧权限。

推荐：

```text
JWT
只负责 Identity

Member Context
负责实时 Authorization Context
```

# 6. KnowledgeBase

数据库模型：

```text
knowledge_bases
────────────────────────────
id
org_id

name
description

ragflow_dataset_id

embedding_model
chunk_method
parser_config

owner_member_id

status
created_at
updated_at
deleted_at
```

状态：

```text
PROVISIONING
ACTIVE
UPDATING
ERROR
DELETING
DELETED
```

创建知识库流程：

```text
POST /knowledge-bases
        ↓
验证 Member
        ↓
创建本地 KnowledgeBase
PROVISIONING
        ↓
RAGFlow
POST /api/v1/datasets
        ↓
取得 ragflow_dataset_id
        ↓
更新本地 KnowledgeBase
ACTIVE
```

RAGFlow Dataset 建议统一：

```json
{
  "name": "销售产品知识库",
  "permission": "me",
  "embedding_model": "...",
  "chunk_method": "naive"
}
```

RAGFlow Dataset 自身只有粗粒度的：

```text
me
team
```

管理权限。

企业 Knowledge ACL 不应该映射成 RAGFlow `team`。

推荐所有 nodeskclaw 托管知识库：

```text
permission = me
```

统一由一个 Knowledge Service RAGFlow Service Account 管理。

这样用户无法绕过：

```text
nodeskclaw-knowledge
```

直接访问 RAGFlow 数据。


```text

subject_type
subject_id
```

其中：

```text

```


# 8. SourceFile 是整个权限系统的核心

RAGFlow 的 Document 不能直接成为我们的源文件主表。

必须定义：

```text
source_files
```

一个 `SourceFile` 是业务逻辑文件。

例如：

```text
2026销售政策.pdf
```

不管以后更新多少次，始终只有：

```text
source_file_id = sf_001
```

表结构：

```text
source_files
─────────────────────────
id
org_id
knowledge_base_id

file_name
mime_type

owner_member_id

active_version_id

status

created_at
updated_at
deleted_at
```

这里的：

```text
source_file_id
```

就是以后权限过滤的最重要 ID。

```text

```

这样以后：


都有稳定基础。

# 10. 文件 ACL

文件默认：

```text
继承 KnowledgeBase ACL
```

只有存在特殊需求时才添加：

```text
source_file_acl
```

表：

```text
source_file_acl
──────────────────────
id
source_file_id

subject_type
subject_id

permission
effect

created_by_member_id
created_at
```

文件权限建议至少包括：

```text

UPDATE
DELETE
MANAGE_ACL
```

```text
KnowledgeBase READ
        ↓
File ACL
        ↓
Effective READ
```

```text
File DENY > File ALLOW > KnowledgeBase ACL
```

这样一个知识库可以组织公开，但其中：

```text
薪酬文件

合同文件
```

# 11. RAGFlow metadata 如何记录 SourceFile ID

这里不建议修改 RAGFlow Chunk。

RAGFlow v0.24 的 Chunk Update API 公开支持的是：

```text
content
important_keywords
available
```

没有提供任意：

```text
chunk.meta_fields
```

更新能力。

所以如果要求：

> 把 source_file_id 直接增加成 RAGFlow Chunk 数据表字段

就需要修改 RAGFlow。

这与：

> 不改变 RAGFlow 产品原结构

冲突。

正确做法是：

```text
SourceFile ID
        ↓
RAGFlow Document.meta_fields
        ↓
Chunk Retrieval
        ↓
document_metadata
```

RAGFlow v0.24 支持：

```http
PUT /api/v1/datasets/{dataset_id}/documents/{document_id}
```

写：

```json
{
  "meta_fields": {
    "nk_source_file_id": "sf_001",
    "nk_file_version_id": "sfv_003",
    "nk_knowledge_base_id": "kb_001",
    "nk_org_id": "org_001"
  }
}
```

Document API 原生支持 `meta_fields`。

而 RAGFlow 的引用结果会在每个检索 Chunk 中返回：

```json
{
  "id": "chunk_xxx",
  "document_id": "...",
  "document_name": "...",

  "document_metadata": {
    "nk_source_file_id": "sf_001"
  },

  "dataset_id": "...",
  "similarity": 0.87
}
```

RAGFlow v0.24 的返回示例已经明确包含：

```text
chunk
→ document_id
→ document_metadata
```

因此从 nodeskclaw 的视角：

```text
这就是 Chunk 的 Source Metadata
```

无需修改 Chunk Schema。

---

# 12. Metadata 只保存身份，不保存 ACL

不要这样写：

```json
{
  "allowed_users": [
    "member_1",
    "member_2",
    "member_3"
  ]
}
```

也不要写：

```json
{
  "allowed_departments": [...],
  "denied_users": [...]
}
```

推荐只保存：

```json
{
  "nk_source_file_id": "sf_001",
  "nk_file_version_id": "sfv_003",
  "nk_knowledge_base_id": "kb_001",
  "nk_org_id": "org_001"
}
```

原因是：

```text
ACL 是动态的
文件身份是稳定的
```

如果员工离职或者权限被删除：

```text
ACL DB 修改
        ↓
立即生效
```

不需要：

```text
重新切片
重新 Embedding
重新更新所有 Chunk
```

这是整个安全架构最重要的设计原则。

# 13. 文件上传完整流程

RAGFlow Document 上传是：

```http
POST /api/v1/datasets/{dataset_id}/documents
```

上传之后返回 `document_id`，初始状态示例为 `UNSTART`；解析可以再通过 `/api/v1/datasets/{dataset_id}/chunks` 指定 `document_ids` 启动。

因此 nodeskclaw 的流程应该严格控制顺序：

```text
Desktop 上传文件
       ↓
nodeskclaw-knowledge
       ↓
验证 MEMBER
       ↓
验证 KB.UPLOAD
       ↓
创建 source_file_id
sf_001
       ↓
创建 version
sfv_001
       ↓
RAGFlow Upload
       ↓
ragflow_document_id
       ↓
更新 Document.meta_fields

nk_source_file_id
nk_file_version_id
nk_knowledge_base_id
nk_org_id
       ↓
启动 Parse
       ↓
等待 Parsing
       ↓
ACTIVE
```

特别注意：

```text
必须先写 metadata
再启动 parse
```

这样整个文件生命周期从一开始就具有稳定 Source Identity。

# 14. Ingestion Job

由于：

```text
上传
metadata 更新
Parse
Embedding
Index
```

属于多个外部操作，不能放在一个数据库事务中。

因此需要：

```text
knowledge_ingestion_jobs
```

状态：

```text
PENDING
UPLOADING
RAGFLOW_UPLOADED
METADATA_SYNCED
PARSING
VALIDATING
ACTIVE
FAILED
CANCELLED
```

记录：

```text
job_id
source_file_id
file_version_id
ragflow_document_id
status
progress
error_code
error_message
retry_count
created_by_member_id
created_at
updated_at
```

如果：

```text
RAGFlow 上传成功
但 metadata 写入失败
```

则：

```text
不允许开始 parse
```

如果：

```text
Parse 失败
```

则：

```text
SourceFile 仍存在
Version = FAILED
允许重新解析
```

# 15. 文件更新

更新：

```text
2026销售政策.pdf
```

不要覆盖旧 Document。

采用：

```text
Blue / Green Document
```

流程：

```text
SourceFile sf_001

v1 ACTIVE
│
├── 上传 v2
│
├── RAGFlow Document B
│
├── metadata
│
├── parse
│
└── validate
       ↓
成功
       ↓
active_version = v2
       ↓
v1 SUPERSEDED
```

这样新文件解析失败：

```text
v1 仍然可以继续提供检索
```

不会导致生产知识突然消失。

旧版本 Document 可以利用 RAGFlow Document `enabled=0` 使其不参与当前知识库。RAGFlow v0.24 Document Update API提供了 `enabled` 控制。

# 18. KnowledgeSet Embedding 约束

RAGFlow Retrieval 可以指定：

```text
document_ids
```

但官方 API 明确要求所选 Document 使用相同 Embedding Model，否则会出错。

因此第一版强烈建议：

```text
一个 KnowledgeSet
只能绑定
Embedding Model 相同的 KnowledgeBase
```

创建绑定时验证：

```text
KB-A bge-m3
KB-B bge-m3
KB-C bge-m3

→ 可以绑定
```

而：

```text
KB-D text-embedding-v4

→ 拒绝绑定
```

以后如果确实需要异构 Embedding：

```text
按模型分组 Retrieval
        ↓
多路召回
        ↓
RRF
        ↓
统一 Rerank
```

第一版不需要增加这个复杂度。

# 19. Retrieval Security Gateway

这是整个 `nodeskclaw-knowledge` 最核心的模块。

用户请求：

```json
{
  "knowledge_set_id": "ks_001",
  "query": "产品 A 的保修政策是什么？"
}
```

不能直接：

```text
knowledge_set
   ↓
dataset_ids
   ↓
RAGFlow
```

正确流程：

```text
1. Resolve Member
        ↓
2. Resolve KnowledgeSet
        ↓
3. Resolve KnowledgeBases
        ↓
4. KB ACL
        ↓
5. SourceFile ACL
        ↓
6. 得到 Authorized SourceFiles
        ↓
7. 得到 Authorized RAGFlow Documents
        ↓
8. RAGFlow Retrieval
        ↓
9. Chunk Security Cleaner
        ↓
10. Safe Chunks
        ↓
11. LLM
```

# 20. 检索前过滤

例如数据集：

```text
销售数据集

KB-A
  doc-A
  doc-B
  doc-C

KB-B
  doc-D
  doc-E
```

张三有权限：

```text
doc-A
doc-C
doc-E
```

nodeskclaw-knowledge 首先算出：

```text
source_file_id:
sf-A
sf-C
sf-E
```

再映射成：

```text
ragflow_document_id:
doc-A
doc-C
doc-E
```

最终调用：

```json
{
  "question": "...",

  "dataset_ids": [
    "dataset-A",
    "dataset-B"
  ],

  "document_ids": [
    "doc-A",
    "doc-C",
    "doc-E"
  ]
}
```

RAGFlow Retrieval 原生同时支持：

```text
dataset_ids
document_ids
metadata_condition
```

这形成第一层：

```text
Pre Retrieval Security Filter
```

---

# 21. 为什么不能只依赖 metadata_condition

v0.24 已经支持：

```json
"metadata_condition": {
  "logic": "and",
  "conditions": [...]
}
```

进行检索过滤。

但不建议把它作为：

```text
唯一 ACL 安全边界
```

原因不是它不能用，而是：

```text
RAGFlow 是 Retrieval Engine
不是企业 Authorization Engine
```

而且 RAGFlow 后续 v0.25.x 的发布说明仍然包含 metadata filtering 的实现优化和 metadata 可见性修复，说明这个机制应该被视为检索能力，而不是唯一的安全隔离机制。

因此：

```text
document_ids
作为权限预过滤

metadata
作为身份映射 / Retrieval 辅助

nodeskclaw ACL
作为最终 Authority
```

# 22. 输出前 Chunk Security Cleaner

即使已经 Pre Filter：

```text
仍必须再过滤一次。
```

RAGFlow 返回：

```json
{
  "id": "chunk_001",

  "document_id": "rag_doc_001",

  "document_metadata": {
    "nk_source_file_id": "sf_001",
    "nk_file_version_id": "sfv_002"
  },

  "content": "...",
  "similarity": 0.88
}
```

Cleaner：

```text
chunk
  ↓
读取 nk_source_file_id
  ↓
sf_001
  ↓
检查 Authorized Source File Set
  ↓
ALLOW?
```

如果：

```text
NO
```

直接：

```text
DROP CHUNK
```

禁止进入：

```text
Prompt
LLM
Citation
Chat History
```

# 29. Retrieval Service 内部结构

推荐明确拆成：

```text
RetrievalService
      │
      ├── MemberContextService
      │
      ├── PermissionService
      │

      ├── RagflowClient
      │

      │

```

核心伪代码：

```python
async def retrieve(member, knowledge_set_id, query):

    knowledge_set = await set_repo.get(knowledge_set_id)

    kb_list = await set_repo.list_knowledge_bases(
        knowledge_set_id
    )

    access_plan = await permission_service.build_access_plan(
        member=member,
        knowledge_bases=kb_list,
    )

    ragflow_result = await ragflow.retrieve(
        question=query,
        dataset_ids=access_plan.dataset_ids,
        document_ids=access_plan.document_ids,
    )

    safe_chunks = await chunk_security.clean(
        member=member,
        chunks=ragflow_result.chunks,
        allowed_source_file_ids=access_plan.source_file_ids,
    )

    return safe_chunks
```


```text
任何内容都不能进入 LLM。
```

# 30. AccessPlan 优化

并不是每次都必须把知识库所有 Document ID 发给 RAGFlow。

可以将权限计算结果分为：

```text

FILTERED_ACCESS
NO_ACCESS
```

如果：

```text
张三对整个 KnowledgeBase
没有任何 File DENY
```

则：

```text
FULL_ACCESS
```

直接传：

```text
dataset_id
```

不必传 5000 个 document_id。

如果：

```text

```

则：

```text
FILTERED_ACCESS
```

才生成：

```text
document_ids
```

这会显著降低大知识库检索时的请求体大小。

# 31. ACL Cache

```text

```

```text

```

不要只依赖长 TTL。



可以作为诊断 metadata 写 RAGFlow，但不能成为真正权限来源。

# 35. 第一阶段验收标准

必须满足：

```text
1. Knowledge 用户全部来自 nodeskclaw OrgMembership。

2. nodeskclaw-knowledge 不存在独立员工账号体系。

3. 一个 KnowledgeBase 对应一个 RAGFlow Dataset。

4. 一个 SourceFile 有稳定 source_file_id。

5. 每个 RAGFlow Document metadata 必须包含：
   nk_source_file_id
   nk_file_version_id
   nk_knowledge_base_id
   nk_org_id

6. SourceFile ACL 不写入 RAGFlow。

7. KnowledgeSet 不在 RAGFlow 创建新的 Dataset。

8. KnowledgeSet 可以聚合多个 KnowledgeBase。

9. Retrieval 前必须经过 ACL。

10. 非完整 KB 权限必须限定 authorized document_ids。

11. RAGFlow 返回 Chunk 后必须再次执行 SourceFile ACL 清洗。

12. Unauthorized Chunk 不得进入 LLM Context。

13. Citation 查看原文件必须重新鉴权。

14. RAGFlow API Key 不得暴露给 Desktop。

15. ACL 修改后不需要重新 Parse / Embedding 即可生效。

16. 文件更新生成新 FileVersion，不覆盖当前有效版本。

17. 新版本解析失败不得影响旧 ACTIVE 版本。

18. 全部 RAGFlow 操作只通过 RagflowClient Adapter。

19. nodeskclaw-knowledge 不直接修改 RAGFlow DB。

20. RAGFlow 可以独立升级而不改变 Knowledge 领域模型。
```

# 36. 最终架构结论

这一版最重要的对象不是 Chunk，而是：

```text
SourceFile
```

最终关系应当理解为：

```text
Member
  │
  │ ACL
  ▼
SourceFile
  │
  │ Identity
  ▼
RAGFlow Document
  │
  ▼
Chunk
```

也就是说：

```text
权限属于 SourceFile

而不是
Chunk
```

Chunk 只携带：

```text
source_file_id
```

从而能够返回：

```text
Chunk
  ↓
SourceFile
  ↓
ACL
  ↓
Member
```

完整权限链。

因此最终的知识检索安全链是：

```text
Member
   ↓
KnowledgeSet
   ↓
KnowledgeBase ACL
   ↓
SourceFile ACL
   ↓
Authorized RAGFlow Documents
   ↓
RAGFlow Retrieval
   ↓
document_metadata.source_file_id
   ↓
Chunk Security Cleaner
   ↓
Safe Context
   ↓
LLM
```

这套结构既满足企业权限治理，又保持 RAGFlow 完全原生。

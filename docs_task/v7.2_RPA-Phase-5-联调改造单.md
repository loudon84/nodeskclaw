# nodeskclaw-task：RPA Phase 5 联调改造单

## Summary

截至 2026-07-15，测试机 Task 已有 Worker、Run、Event、Artifact、HumanAction 接口及相关表，但存在两个硬阻塞：

- `WorkerLeaseResponse` 只有 `taskId/runId/leaseId/workflowBindingId/portalAccountId/rpaFlowId/input`，缺少 Engine 执行快照。
- renew 当前返回 `data=null`，Engine 必须获得新的 `leaseExpiresAt`。

目标是让 Task 能投递确定版本的 Mock SRM RunCommand，并正确接收 `SUCCESS / FAILED / WAITING_HUMAN`、日志和证据。Mock Portal URL 决定由 lease 快照携带；人工处理不恢复或自动重跑原浏览器。

## 数据与绑定改造

- `workflow_bindings` 增加：
  - `rpa_flow_version_id VARCHAR(36)`：Engine Registry 的版本 UUID，不建立跨库外键。
  - `flow_checksum_snapshot VARCHAR(64)`：去掉 `sha256:` 前缀后的 64 位小写 SHA256。
- `rpa_runs` 增加 `command_snapshot JSONB NOT NULL DEFAULT '{}'`，首次 lease 时保存完整不可变执行快照；renew 和同一 Run 的重新投递必须复用该快照，不能重新读取“最新绑定”。
- 建议增加幂等约束：
  - `step_runs(run_id, step_id)` 活跃记录唯一。
  - `artifacts(run_id, storage_key)` 活跃记录唯一。
  - 同一 `run_id` 只能有一个 `PENDING/OPEN` HumanAction。
- 旧绑定不自动选择最新 Flow，也不自动补错误版本。无法从 Engine 校验并回填的绑定可以继续查询，但禁止 lease，返回明确业务错误 `BINDING_FLOW_SNAPSHOT_MISSING`。
- 创建或更新 WorkflowBinding 时调用 Engine：
  - `POST http://192.168.102.247:4610/api/v1/flow-versions/validate-binding`
  - Header：`X-Actor-Id`；TENANT Flow 同时传 `X-Tenant-Id`。
  - Body：`rpaFlowId + rpaFlowVersion + workflowCode`。
  - 仅允许绑定 `valid=true` 的已发布版本，并保存返回的 version ID、checksum。
- `workflowCode` 必须取 `workflow_templates.code`，不能用 `automation_tasks.task_type` 替代。
- Task input 保持不透明原样传递。Phase 5 三条任务必须使用：
  - `{"po_no":"PO-20260708-001"}`
  - `{"po_no":"PO-NOT-FOUND"}`
  - `{"po_no":"PO-MANUAL-001"}`
  - 不要转换成 `poNo`。

## Worker API 契约

保持当前混合风格：Worker 请求体使用 snake_case，响应 `data` 使用 camelCase；成功信封继续为 `code=0`。

### 1. Lease

`POST /api/v1/autotask/worker-api/tasks/lease`

请求：

```json
{
  "worker_id": "server-worker-001",
  "capabilities": [
    "PLAYWRIGHT_CDP",
    "BROWSER_SESSION_MANAGED"
  ],
  "limit": 1
}
```

`capabilities` 表示 Worker 能力，不能继续使用 Postman 里的 `["fetch_po"]`。无可执行任务时返回 `data: null`。

有任务时，`data` 必须完整返回：

```json
{
  "taskId": "task-id",
  "runId": "run-id",
  "leaseId": "lease-id",
  "workflowBindingId": "binding-id",
  "portalAccountId": "portal-account-id",
  "rpaFlowId": "rpa_flow_mock_srm_fetch_po",
  "input": {
    "po_no": "PO-20260708-001"
  },
  "tenantId": "tenant-id",
  "workflowTemplateId": "template-id",
  "workflowCode": "srm_fetch_po",
  "rpaEngineType": "PLAYWRIGHT_CDP",
  "rpaFlowVersion": "1.0.0",
  "credentialRef": "credential-ref-mock-srm",
  "config": {
    "portalUrl": "http://192.168.102.247:4600",
    "browserSession": {
      "mode": "MANAGED",
      "headless": true,
      "channel": "chrome",
      "profileRef": null,
      "cdpEndpointRef": null,
      "closePolicy": "CLOSE_ON_FINISH"
    }
  },
  "leaseExpiresAt": "2026-07-15T10:01:00Z"
}
```

字段来源固定为：

- `tenantId`：`automation_tasks.tenant_id`
- `workflowTemplateId`：绑定的模板 ID
- `workflowCode`：`workflow_templates.code`
- `rpaEngineType/rpaFlowId/rpaFlowVersion`：绑定快照
- `credentialRef/portalUrl`：`portal_accounts`
- `browserSession`：`workflow_bindings.config`
- `leaseExpiresAt`：`worker_leases.lease_expires_at`

Lease 事务需要：

- 锁定一个 `QUEUED` 任务，校验 Task、Binding、Template、Portal tenant 一致且状态可用。
- 首次 lease 创建 Run、WorkerLease 和 `command_snapshot`，将 Task/Run 置为 `RUNNING`。
- 初始租约建议 60 秒；两个 Worker 并发请求不能领取同一个任务。
- 同一 Run 因租约过期重新投递时使用新 `leaseId`、原 `runId` 和原 `command_snapshot`。
- 不得通过“最新发布版本”替代绑定版本。

### 2. Renew

`POST /api/v1/autotask/worker-api/tasks/{task_id}/lease/renew`

请求保持：

```json
{
  "worker_id": "server-worker-001",
  "lease_id": "lease-id"
}
```

当前 `data=null` 必须改为：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "leaseExpiresAt": "2026-07-15T10:02:00Z"
  }
}
```

续租必须校验 `taskId + workerId + leaseId` 一致、租约仍有效，原子更新数据库后返回带时区的 RFC3339 时间。错 Worker、错 lease 或已过期租约必须拒绝，不能静默返回成功。

### 3. Events 与 StepRun 投影

现有接口保持：

`POST /api/v1/autotask/worker-api/runs/{runId}/events`

请求字段仍为 snake_case：

```json
{
  "worker_id": "server-worker-001",
  "type": "STEP_STARTED",
  "level": "INFO",
  "message": "Searching for purchase order",
  "payload": {
    "stepId": "srm.search_po",
    "stepType": "srm.search_po"
  }
}
```

除保存 `run_events` 外，Task 应投影以下事件：

- `STEP_STARTED`：upsert StepRun=`RUNNING`，更新 Run/Task 当前步骤。
- `STEP_SUCCEEDED`：StepRun=`SUCCESS`。
- `STEP_FAILED`：StepRun=`FAILED`。
- `STEP_WAITING_HUMAN`：StepRun=`WAITING_HUMAN`。
- `FLOW_LOG/RUNTIME_*`：只保存为 RunEvent，不创建 StepRun。

缺少 `stepName` 时用 `stepId` 作为显示名。

### 4. Artifact

现有三段式协议继续使用：

1. `POST /api/v1/autotask/artifacts/upload-url`
2. Engine 对 `uploadUrl` 直接 PUT 文件
3. `POST /api/v1/autotask/worker-api/runs/{runId}/artifacts`

请求体保持 snake_case，响应 upload target 保持 camelCase。Task 必须：

- 生成 Engine 可访问的 MinIO/S3 签名 PUT URL。
- `storageKey` 按 tenant/task/run 隔离。
- 登记 metadata 前校验 run 属于 task、storageKey 属于本次上传范围。
- 同一 `runId + storageKey` 重复回调视为幂等成功。
- 截图、PDF、Trace 均可在现有 Artifact 查询/下载接口中看到。

## Finish、状态机和 HumanAction

`POST /api/v1/autotask/worker-api/runs/{runId}/finish`

请求仍使用：

```json
{
  "status": "WAITING_HUMAN",
  "error_code": "HUMAN_VERIFICATION_REQUIRED",
  "error_message": "Mock SRM requires CAPTCHA or MFA verification"
}
```

finish 必须锁定 Run 和 Task，并在同一事务中完成状态更新：

- `SUCCESS`
  - Run=`SUCCESS`、设置 `ended_at`
  - Task=`SUCCESS`、progress=100
- `FAILED`
  - Run=`FAILED`、保存 error code/message、设置 `ended_at`
  - Task=`FAILED`
- `WAITING_HUMAN`
  - Run=`WAITING_HUMAN`、保存错误并设置 `ended_at`
  - Task=`WAITING_HUMAN`
  - 创建一个 `PENDING` HumanAction：
    - type=`CAPTCHA_OR_MFA`
    - title=`需要人工完成 Mock SRM 验证`
    - instruction=`请打开门户完成验证；服务器浏览器会话已关闭`
    - targetUrl=`portal_accounts.portal_url`
    - payload 保存 runId、stepId、errorCode；stepId 可从最后一条 `STEP_WAITING_HUMAN` 事件取得

finish 幂等规则：

- 相同 Run、相同 terminal status 重复提交返回成功，不重复创建 HumanAction。
- terminal status 已存在但新状态不同，返回冲突，不允许覆盖历史结果。

HumanAction 按已确认的类型 A 模式处理：

- `open`：Action=`OPEN`，Task 保持 `WAITING_HUMAN`。
- `confirm` 且 `resume_running=false`：Action=`CONFIRMED`，Task=`SUCCESS`，记录“人工完成”消息；原 Run 保持 `WAITING_HUMAN`，不创建新 Run、不重新入队。
- `confirm` 且 `resume_running=true`：返回 `HUMAN_RESUME_NOT_SUPPORTED`，不能把 Task 直接改回 RUNNING。
- `cancel`：Action=`CANCELLED`，Task=`CANCELLED`。
- 所有操作都不恢复原 Playwright Context。

## 测试与联调验收

Task 同事必须补齐：

- OpenAPI 模型测试：lease 新字段全部 required；renew 返回 `leaseExpiresAt`。
- Repository 并发测试：两个 Worker 只能有一个成功领取同一任务。
- 快照测试：领取后修改 Binding/Portal，renew 或重新投递仍使用原 `command_snapshot`。
- Lease 错误测试：缺版本、缺 portalUrl、非 MANAGED、过期租约、Worker 不匹配均明确拒绝。
- finish 三状态测试及重复 finish 幂等测试。
- WAITING_HUMAN 重复 finish 只创建一个 HumanAction。
- STEP 事件正确投影到 StepRun。
- upload-url、签名 PUT、Artifact metadata、下载 URL 完整测试。
- 修复 Postman collection 的乱码/无效 JSON，并将 Worker 请求示例改为真实 snake_case。

专用联调数据：

- Portal URL：`http://192.168.102.247:4600`
- Template code：`srm_fetch_po`
- Flow：`rpa_flow_mock_srm_fetch_po / 1.0.0`
- Binding browser channel：测试机使用 `chrome`
- 三个专用任务分别使用成功、失败、人工 PO
- 只在 Task 测试通过后，Engine 才开启 `WORKER_LEASE_ENABLED=true`

Task 侧不负责上传 Flow、启动浏览器或返回明文凭据。Task 只保存和下发 `credentialRef`；Mock 凭据解析器仍由 Engine/凭据服务另行接入。测试环境暂时沿用 Worker API 无 JWT，服务账号鉴权作为后续生产加固项。

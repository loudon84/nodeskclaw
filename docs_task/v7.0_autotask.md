# PRD 2：nodeskclaw-task 后端项目实现方案

## 1. 项目定位

在 `nodeskclaw` monorepo 中新增与 `nodeskclaw-backend` 平级的新项目：

```text
nodeskclaw-task
```

定位：

```text
nodeskclaw-backend
= 身份认证
= 用户 / 组织 / 角色
= JWT / Session
= 基础权限
= 系统审计主体

nodeskclaw-task
= AutoTask 业务数据接口
= Portal Account 管理
= Workflow Template 管理
= Workflow Binding 管理
= Automation Task 管理
= Task Message 管理
= RPA Run / RunEvent 管理
= Human Action 管理
= Artifact Metadata 管理
= RPA Worker Dispatch API
= AutoTask MCP Tools API
```

不要把 AutoTask 任务模块直接塞进 `nodeskclaw-backend`。原因：

```text
1. nodeskclaw-backend 当前职责已经是 DeskClaw API 中枢、认证、组织、部署、工作区、运行时管理等
2. AutoTask 属于垂直业务域，模型和状态机会快速膨胀
3. RPA RunEvent / Artifact / Worker Lease 会产生高频写入
4. 独立服务更容易后续拆队列、拆存储、拆 RPA 调度
```

nodeskclaw 当前仓库已有 `nodeskclaw-backend`、`nodeskclaw-portal`、`nodeskclaw-llm-proxy`、`nodeskclaw-artifacts` 等平级项目；`nodeskclaw-backend` 的 README 明确其技术栈为 Python 3.12 + FastAPI + SQLAlchemy asyncio + PostgreSQL + JWT。

## 2. 总体架构

```text
AutoTask Studio Client
  ↓ Auth
nodeskclaw-backend
  ↓ JWT / User / Org / Role
nodeskclaw-task
  ↓ Task / Portal / Workflow / Run / Artifact
RPA Engine
  ↓ Playwright / CDP
客户 SRM / 供应商 Portal
```

系统边界：

```text
AutoTask Client 不直接访问 nodeskclaw-backend 的业务表
nodeskclaw-task 不签发用户主 Token
nodeskclaw-task 只验证 nodeskclaw-backend 签发的 JWT
RPA Engine 不直接操作业务数据库
RPA Engine 通过 nodeskclaw-task Worker API 上报状态
```

既有总体架构已明确：`nodeskclaw-backend` 负责用户登录、组织、角色、权限；`nodeskclaw-task` 负责 AutoTask API、Portal Account、Workflow Template、Task Dispatch、Run State、Human Action、Artifact Metadata、MCP Server；RPA Engine 只做 Playwright/CDP 执行。

## 4. 认证与权限接入

### 4.1 Token 来源

`nodeskclaw-task` 不提供登录接口。登录仍走：

```text
nodeskclaw-backend /api/v1/auth/account-login
nodeskclaw-backend /api/v1/auth/me
nodeskclaw-backend /api/v1/auth/refresh
nodeskclaw-backend /api/v1/auth/logout
```

nodeskclaw-backend 已有 `/api/v1/auth` 模块，并且 `LoginResponse` 返回 `access_token / refresh_token / token_type / expires_in / user`。

### 4.2 Token 校验

`nodeskclaw-task` 需要复用 nodeskclaw-backend 的 JWT 配置：

```env
JWT_SECRET=...
JWT_ALGORITHM=HS256
JWT_EXPIRE_HOURS=...
```

校验逻辑：

```text
1. 从 Authorization: Bearer <token> 读取 token
2. decode JWT
3. 校验 type == access
4. 读取 sub 作为 user_id
5. 从 nodeskclaw-task 本地 user cache 或远程 backend 获取用户摘要
6. 注入 current_user / current_org_id
```

nodeskclaw-backend 当前 `create_access_token()` 会写入 `sub / exp / type=access`，`get_current_user()` 会从 Bearer token 中解析用户并校验用户状态。

### 4.3 用户同步策略

第一期采用轻量用户镜像表：

```text
task_user_cache
├─ user_id
├─ name
├─ email
├─ current_org_id
├─ org_role
├─ portal_org_role
├─ is_super_admin
├─ synced_at
```

同步方式：

```text
1. 每次请求如本地无 user cache，则调用 nodeskclaw-backend /api/v1/auth/me
2. 写入 task_user_cache
3. 后续请求优先用 JWT + cache
4. cache 超过 10 分钟则后台刷新
```

生产版本可改成内部 introspection API 或共享用户服务。

## 7. 任务状态机

```text
DRAFT
  ↓
READY
  ↓
QUEUED
  ↓
LEASED
  ↓
RUNNING
  ├─ WAITING_HUMAN
  │    ↓
  │  HUMAN_OPERATING
  │    ↓
  │  SUCCESS_MANUAL / RUNNING / FAILED
  │
  ├─ SUCCESS
  ├─ PARTIAL_SUCCESS
  ├─ FAILED
  └─ CANCELLED
```

说明：

```text
LEASED
  表示任务已被 Worker 领取，但还未开始执行。
  这是分布式 Worker 防重复执行的关键状态。

WAITING_HUMAN
  表示 RPA 或业务规则要求人工处理。

HUMAN_OPERATING
  表示用户已经点击快速打开或接管，正在处理。

SUCCESS_MANUAL
  表示任务不是由 RPA 自动完成，而是人工确认完成。
```

## 10. MCP API

MCP 只暴露稳定业务能力，不暴露数据库和 RPA 内部细节：

```text
autotask.portal.search
autotask.portal.get
autotask.workflow.list
autotask.task.create
autotask.task.get
autotask.task.get_status
autotask.task.list_messages
autotask.human_action.list_pending
autotask.human_action.confirm
autotask.artifact.list
```

原则：

```text
1. MCP 调用必须验证 JWT 或 service token
2. MCP 不绕过 PortalAccessGrant
3. MCP 创建任务后仍进入标准任务状态机
4. MCP 不直接调用 Playwright
5. MCP 只调用 nodeskclaw-task service 层
```
